# Exclusive judge invitations — prepared, hosted verification pending

The web and desktop boot screens accept an owner-issued one-use invitation. No public registration or shared account password is used. Each invitation atomically claims one exclusive separate calendar and creates a cryptographically random workspace, its own uploads, journals, plans and approval receipts. Tokens are submitted in a POST body, never a URL. Invitations expire; workspace sessions expire within 1–12 hours. Expired leases remain retired and are never automatically reassigned, even after local workspace deletion.

After organizer credit activation, hosting and runtime Calendar access are verified:

1. Obtain explicit owner approval for one empty separate demo calendar per visitor. The currently authorized CampusPulse RELAY Demo calendar can support one exclusive visitor; additional calendars require owner authorization. Never use a primary calendar. Share only each approved calendar with the actual MCP runtime service identity, granting event editing. Verify access and an empty full event listing.
2. In the configured D: project environment, run `scripts/prepare_judge.py --calendar-id ACTUAL_ID --hours 4 --confirm-exclusive-owned-calendar`. It reads live Calendar state, refuses a nonempty/reused calendar, registers the lease in the configured store and saves the invitation under `.local/judge-private/` on D:. No calendars are automatically created or cleared. Live preparation is currently blocked on cloud access.
3. Enable `RELAY_JUDGE_ENABLED=true` on the gateway only after the real smoke succeeds. Set `RELAY_GITHUB_REPO` to the dedicated repository. Share the private invitation with its intended judge yourself; never include it in the public repo, recordings or chat. The app permits unseen files and unscripted requests. Draft availability is explicit; no fixture is represented as a live observation.
4. Defaults reserve 100 of 300 daily model requests for judges; non-judge traffic cannot consume that reserve. Per-workspace limits still apply. Tune to the measured approved credit envelope. Request limits are not a guaranteed dollar cap.
5. Test two clean browser identities, concurrent claim, replay, expired sessions, different uploads and exact Calendar targets. Verify real approved writes/read-back and external event links; the current 56-test local suite covers isolation logic, not hosted credentials or actual Calendar access.
6. After the judging window, retire invitations, review owned event receipts, remove only verified unchanged RELAY events using guarded undo, and retain/delete private workspace data according to the owner's decision. No automatic calendar reset or reuse is implemented.
