# Calendar: implementation, account setup and actual acceptance gates

Status: **app client/consent/live acceptance pending**. Google Calendar is a required product integration and a voluntary per-visitor connection. Public Gemini never requires Google login, an invitation, Calendar consent or a visitor API key. A Calendar connector in the coding environment does not grant the application OAuth access.

The current app defaults to `openid`, email and `calendar.app.created`: only app-created secondary calendars and their events. It does not read the visitor's pre-existing personal calendar. Existing-calendar access is a separate explicit flow (`/api/auth/start?existing=true`) using events and calendar-list read scopes; it must undergo its own scope/verification review. No shared public write calendar. The previously returned owner demo calendar ID remains in `docs/connections.json`; it is not assigned to anonymous visitors.

Implemented boundary: capability workspace → state/PKCE + browser state cookie → Google OAuth → verified identity bound to the SAME workspace → encrypted refresh credentials → explicit Create separate study calendar or authorized target selection → immutable exact action preview → explicit UI approval → deterministic event IDs/read-back/ETag/guarded undo. Consent alone never approves writes. Source facts and progress do not move to a Google-subject workspace. Disconnect deletes the local token and attempts Google revocation; existing events are preserved. A timeout creating a Calendar is an unknown external result and blocks automatic creation retry. Temporary hosting can lose credentials on restart: reconnect is then required. Private event payloads and mutation tools are excluded from unpaid Gemini.

## Exact owner setup, no billing or API-key sharing

1. In Google Cloud Console select the existing permitted free project `gen-lang-client-0595303951` for ordinary Calendar OAuth only; do not attach billing, enable a trial, enter a card or select it for organizer GCP credits by assumption. Enable Google Calendar API if currently disabled. Stop if any payment/billing activation is required.
2. Google Auth Platform → Branding/Audience/Data Access: inspect current app and publishing status. Configure CampusPulse RELAY with actual owner support/developer contacts, public home and privacy URLs. For the initial separate-calendar flow select only the three scopes above. Record the Console's actual classification/verification requirements; `calendar.app.created` does not prove verification is unnecessary. Do not bypass warnings, add arbitrary judges as test users or change publishing status without owner approval. Testing restrictions and Workspace administrator policies are real blockers to independent public Calendar access.
3. Clients → Create OAuth client → Web application. Exact authorized redirect URI: `https://campuspulse-relay-demo.onrender.com/auth/callback`. Do not create a desktop client, service-account key or domain-wide delegation.
4. Save the ID/secret privately on D: with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File D:\projects\CampusPulseRELAY\scripts\configure-calendar.ps1`. Both prompts are hidden; do not send credentials in chat. This prepares local server testing only.
5. Render → existing **Free** campuspulse-relay-demo → Environment: configure server-only `RELAY_OAUTH_CLIENT_ID`, `RELAY_OAUTH_CLIENT_SECRET`, and a distinct Fernet `RELAY_TOKEN_ENCRYPTION_KEY`; `RELAY_GATEWAY_URL` is the HTTPS origin above. Secret values must be entered privately or transferred through an authorized secret path. Save only until the verified source is ready; environment saves/deploys must not accidentally upgrade the service.

Technical configuration is not live acceptance. When enabled: open a clean visitor workspace → Connections → Connect Google in system browser → actual consent → return to the same source/history workspace → Create a separate study calendar → choose its actual returned ID → create a current plan → review exact actions → approve → inspect independent Google event read-back IDs/ETags/links → retry without duplicates → guarded undo → disconnect/revocation. Record actual target timezone, no unrelated event changes, consent cancellation and permission loss. Fault injection is separately labeled. A human must perform Google consent; native picker/banner checks also remain separate human observations.

Official references: [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), [OAuth web flow](https://developers.google.com/identity/protocols/oauth2/web-server), [verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification). No automatic Google app publication or verification submission has been performed.
