# Installed 0.1.1 import failure and correction

The user reported the real Windows picker appearing and the diagnostic `Error invoking remote method 'relay:request': Error: Unsupported application request.` Import success was not confirmed. The original verification profile recorded one native-dialog open/cancel, no selected-file callback and no notification callback. Its gateway log had no matching server exception. The original build did not record rejected route/method metadata, so that particular human attempt cannot be attributed conclusively from historical logs.

Before editing, installed `app.asar` main, preload and renderer bytes matched the working build. The original main SHA-256 was `6040a1775b3cdf0ddc10d6a19cd8e248050d09dd3e1f400d04d87a6a8134de5d`, preload `4fca25d7fe6d70c80db78bb5c3a298b41c08037a8831037a952c0cde4e2132ab`, renderer `4305cba1df75651c00bdb6d07602ed4351101f2a7f7e60436b86efb6fcc0b775`. The later baseline regression captures these packaged hashes again; its `matches_current_source: false` reflects the subsequent fix/build, not a pre-existing packaging mismatch.

The exact diagnostic was reproduced against that original installed executable through its renderer file input: `POST /api/import` reached the restricted IPC handler and was rejected before any gateway upload. No following state refresh occurred for that attempt. The distinct native-dialog branch sent `POST /api/import-native`, imported the file and completed `GET /api/state` successfully. The regression uses an explicitly substituted dialog for repeatability and does not establish human native-picker success. Evidence: [original installed regression](evidence/desktop-import-original.json).

`src/imports.ts` now sends both Electron selection paths as bounded JSON/base64 to the existing `POST /api/import-native` route. Browser uploads still use multipart `/api/import`. The desktop bridge continues rejecting `/api/import`, unsupported methods and unknown paths; its allowlist was retained in `desktop/request-policy.cjs`. The corrected installer and portable package were rebuilt and the installed app was replaced on D:.

The corrected installed regression imports through both selection paths, reads the exact original contents back, checks the state refresh/cache stages, compares packaged main/preload/policy/renderer/HTML bytes with the current build, and asserts that invalid IPC still fails. Two additional policy tests check route/method rejection and diagnostic redaction. Evidence: [corrected installed regression](evidence/desktop-import-regression.json).

`profile/logs/desktop-trace.jsonl` now records native selection → file-read → import-request → state-refresh → snapshot-save stages. Rejections include only the method and sanitized path. Dynamic segments and query values are redacted. Document bytes, filenames/paths, credentials and approval payloads are not written to this trace. Native picker and notification logs remain separate. A gateway rejection, network failure or snapshot failure has its own stage, so a completed import is distinguishable from a subsequent refresh failure.

The corrected app was reopened with the same profile and existing fixture under `.local/native-verification/0.1.1-mvebaaui/`. Real picker appearance is confirmed by the user. The unmodified picker returned the selected fixture at `2026-10-18T21:21:11.437Z`. File read completed, `POST /api/import-native` returned 200, `GET /api/state` returned 200, and snapshot save completed at `21:21:11.505Z`. Independent source read-back matched the fixture exactly. No request was rejected in this real recheck. The user subsequently confirmed that everything worked and the actual notification appeared in the bottom-right corner. Visibility is verified by this explicit human observation, separately from dispatch/show callbacks. No notification click callback was observed, so click/focus behavior remains unverified. See [native results](evidence/desktop-native-result.json). No GCP, Gemini or Google authentication was required.
