# Four additions: decisions, invariants and combined demo

## Progress

Source effort stays in immutable cited facts. Personal estimates use overrides; progress has its own remaining estimate and provenance. Timer/manual logs store exact fractional minutes, stable IDs, revisions and correction history. Logs never imply original-minus-time remaining or completion. Positive remaining rounds **up** to the existing 30-minute grid; zero requires deliberate student completion and satisfies zero-work internal prerequisites. Unknown remaining blocks an unconditional plan instead of guessing. No monitoring of other apps/files occurs.

Only the currently started UI timer sends ten-second monotonic deltas. Server wall time caps accepted increments; a gap above 45 seconds, oversized delta, reload/hidden/closed UI or conflicting revision requires recovery and explicit duration confirmation. Absence is not auto-logged. Server time is not proof of attention. A single tenant SQLite command transaction checks the workspace revision, request ID/body digest and session/log revision, changes history, invalidates plans and increments the revision. Three concurrent identical stops produce one log. Stale edits are rejected. Source/settings/decision/progress/gate fingerprints bind all previews and approvals; both authorization and apply recheck them.

Future plans are previewed separately before adoption. Started/past study blocks remain reference history and existing Calendar events are kept; crossing blocks stay busy. Only eligible future blocks move, with a reason and added/removed diff. Calendar actions retain a separate exact approval boundary. No logging or adoption writes Calendar.

Estimate suggestions require five other completed same-workspace tasks with exact confirmed course and student-declared category, positive corrected logged duration, and an estimate frozen by Start work **before** work began. Manual-only and imported history are excluded. Median actual/frozen ratio is capped 0.5–2, applied to the frozen estimate and rounded up to 30 minutes (maximum 10,080). The sample count/list and insufficient-data state are shown. Explicit acceptance sets a personal estimate; this is a transparent heuristic, not a probability or validated student-outcome model.

## Clarify First

Actual conflicting source deadlines, student-offered positive effort bounds and an explicitly offered availability window generate binary questions. At most three selected questions and eight joint branches run against a versioned copied snapshot. No question invents dates, windows or probabilities. Solver/model-build guards bound the overall local analysis to eight seconds and each solve to one second. Two global jobs and one per workspace are allowed; repeated UI clicks are locked. Cancellation discards results; CP-SAT UNKNOWN remains unknown, never infeasible. Source/progress/gate changes discard stale results/cache.

Question order is deterministic: evaluated impact before unknown; feasibility-changing before unchanged; earliest cited deadline; affected unscheduled minutes; changed blocks; stable ID. Pairs differ in one answer while retaining each tested joint context, exposing interactions such as two individually harmless effort increases jointly overflowing capacity. The selected set, branches, remaining unknowns and approximate scope are visible. No expected-value or entropy claim is made. Evidence choices use source resolution; estimates/availability stay student assumptions. I don't know records the uncertainty without resolving it. Minimal Rescue remains a separate offered-constraint comparison.

## Handoff Radar

Student-linked external PR gates are separate from internal task dependencies. Only fixed `https://api.github.com/repos/{owner}/{repo}/pulls/{positive_number}` reads are supported; explicit `merged` plus `merged_at` is required. Open and closed-unmerged both remain waiting, with their actual distinct observed metadata. Unknown, waiting, condition observed, stale and unavailable are separate states, retaining last known data after errors. Changed source bindings require explicit relinking/revalidation. A waiting gate contributes no assumed future capacity; an optional student ETA is conditional and cannot authorize actions. Observed releases schedule from current time. The latest safe handoff is honestly unknown; no threshold optimization is claimed.

Only the configured repository is available publicly. Optional `RELAY_GATE_REPOS` is a local process/server configuration; it cannot expand a public visitor's scope. Five-minute bounded shared single-flight cache and ETags retain original observation time; 304 records an unchanged confirmation/check time. Freshness expires after 15 minutes. Requests are anonymous public reads, no private credential; redirects are disabled, response max 500 KiB, connect/read timeout ten seconds and streamed elapsed guard twelve seconds. Rate-limit/Retry-After backoff is shared with the existing connector. Polling is demand-driven; no keepalive or notification messages are sent externally.

In-app state is durable; desktop notifications reuse the helper and require a one-time tenant-scoped durable dispatch claim, preventing repeats across tabs/restarts. Dispatch is not visibility/click proof. `observe_handoff_gate(gate_id)` is the narrow MCP contract, sharing the same service and authenticated context; no tenant/repo/calendar/approval tool parameter is accepted. Fourteen tools were actually discovered over local Streamable HTTP; managed Gemini invocation remains pending.
